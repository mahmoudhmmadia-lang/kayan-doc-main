\section{SOPs}
\label{sec:builder-feature-sops}

This page opens the embedded KayanOS Automations studio inside the app, where you build flows that run by themselves when a specific event happens. Instead of an employee remembering the same hand-off every time, the automation reads the record, decides whether work is needed, then creates a record, task, document or notification that the owner reviews. The product documentation says automations run through a KayanOS connection; the connections page explains what the test environment showed. Approval and task flows built entirely inside the app are explained under “Internal SOPs” in the previous chapter.

The names of triggers, actions and their fields come from the embedded studio, not from the app's translations, so most of them appear in English even in the Arabic interface, and these pages give them as they appear on screen. The screens shown were reviewed on the \en{test2} test environment; the other names in the tables come from the product documentation.

\textbf{Path and who uses it:} “Builder” → “Core” → “SOPs”. The page appears for those with forms permission; the owner or administrator who needs to automate a repeated hand-off builds there.

\begin{rcnote}[Example: Horizon]
Horizon wants no new visit request to be lost. So the system administrator builds an automation that starts when a record is created in “Visit requests”, checks that the branch is “Aleppo Branch”, then creates a review task for Sarah Al-Khatib and sends her a notification.
\end{rcnote}

\subsection{Steps and check}
\begin{enumerate}
\item Before building, write one sentence that states the decision, such as: “When a new request is created for a given branch, create one review task.”
\item Open “SOPs”, create a new flow with a name that describes the result, and choose the approved KayanOS connection if the step asks for one.
\item Choose the narrowest trigger for the event, test it with a sample record and review the data that arrived.
\item Add a condition before the first writing action, then add the actions one after another, testing each one.
\item Turn the automation on for a small scope after the tests pass, then review the first real run with the business owner.
\end{enumerate}

\textbf{Check and recovery:} you should find the result in its place inside the app, such as the new task or record, not only in the automation output. If the page stays empty or shows an error, the automation service may not be available in your organization's environment; ask the platform administrator to check it. If an action fails, check the connection first, as the connections page explains.

\section{Automation triggers}
\label{sec:builder-feature-sops-triggers}

A trigger is the event that starts an automation; it is not a subscription to everything that happens in the organization. A good trigger answers one question: what happened, to which record, form or task, and why is this the moment to start the work? So a deliberate action, such as submitting a form for review, is better than watching every edit on a record.

\textbf{Path and who uses it:} “SOPs” → the flow → the trigger step. Used by whoever builds the automation.

\begin{rcnote}[Example: Horizon]
The system administrator chooses the \en{New Record Created} trigger and sets the table to “Visit requests”. They test it with a sample request and see in the output the branch and visit date that the condition will rely on.
\end{rcnote}

\end{rcwarn}

\begin{enumerate}
\item Write the event in one sentence, such as: “When the request moves to the ready-for-review status.”
\item Choose the trigger with the clearest business meaning, then set its source: \en{Table Name}, \en{Form}, \en{Task Type} or \en{Epic Type}.
\item Apply the available narrowing filters, such as \en{Form Versions} and \en{Actions} for a form, or \en{Operations} in \en{Record Changes}.
\item Run the trigger test with one sample record, and review \en{data}, \en{oldData}, \en{changedFields} and \en{action} when they appear.
\item In the following steps, map stable IDs and status values, not names a user could edit.
\end{enumerate}

\textbf{Check and recovery:} the test output should show the event you intended with the data you need. If the automation does not start, review the trigger source and its filters, then repeat the same event on the sample record. If it starts too often, narrow the trigger or add a status-transition condition.

\section{Automation actions}
\label{sec:builder-feature-sops-actions}

An action is the outcome of an automation step: it reads information, creates or updates a record, waits for a later event, coordinates a task, prepares a document, returns a response or sends an internal notification. The preferred order is: read first, then check the condition, then write once, then inform the owner. Choose each action because it produces a needed result, not because it is in the list.

\textbf{Path and who uses it:} “SOPs” → the flow → add a step after the trigger or condition. Used by whoever builds the automation, who also needs access to the records, forms and tasks it uses.

\begin{rcnote}[Example: Horizon]
The system administrator adds \en{Find Records} to look for an open review task for the same request. If none is found, they add \en{Create Task} for Sarah Al-Khatib, then \en{Send Notification} to tell her about the new request.
\end{rcnote}

Do not place a write, execute, role-update, document or notification action directly after an unnarrowed event. Treat \en{Delete Record(s)} and \en{Update Roles} as high risk, and never use \en{Execute} actions to skip a decision that policy assigns to a person.
\end{rcwarn}

\subsection{Steps and check}
\begin{enumerate}
\item Add a read action such as \en{Get Record} or \en{Find Records}, and narrow the search by a stable ID, relationship or status.
\item Add the condition that decides whether to continue, and handle no result, one result and several results deliberately.
\item Add the write action, and map its required fields from the trigger output or the previous step.
\item Add \en{Send Notification}, and set \en{Type} and one of \en{Member ID} or \en{Member Selectors}.
\item Test each action after adding it, and look for its result in its place inside the app.
\end{enumerate}

\textbf{Check and recovery:} a run should create one result in the right place, with no duplicates and no change to other records. If a write is rejected, review the required fields, the target table and the connection's permissions. If a notification is rejected, leave \en{Member Selectors} empty when you set \en{Member ID}.

\section{Automation connections}
\label{sec:builder-feature-sops-connections}

The product documentation says every trigger and action in KayanOS Automations runs through a KayanOS connection. The connection is an organization-level permission boundary the automation runs through, even when its result only touches records inside the app. So confirm it is valid before choosing the trigger or mapping fields when the step asks for it. If the result genuinely needs an external system, that system's connection is an additional authorization; it does not replace the KayanOS connection. On the \en{test2} test environment, KayanOS steps showed no field for choosing a connection, and the “Connections” list was empty although active automations existed; so ask the platform administrator which connection your organization's automations run through if you need to document it.

\textbf{Path and who uses it:} “SOPs” → the “Connections” tab, or the step's connection field when it appears. Chosen by whoever builds the automation and approved by an owner the organization names.

\begin{rcnote}[Example: Horizon]
For the “Visit requests” automation, the system administrator chooses the organization's approved connection, not an employee's personal account. They record that the connection's owner is responsible for renewing it if it expires.
\end{rcnote}

\item Map only approved values, so you do not send the whole record when the target needs one ID or status.
\item Test the connection with a sample record, then document its purpose, scope and review date.
\end{enumerate}

\textbf{Check and recovery:} the editor should accept the connection, and the test should succeed without reaching beyond the approved scope. If the connection has expired or its scope is wrong, correct it through its owner; never solve the problem by choosing a broader connection or a personal account. Never write a password or access token in a field, expression or template.

\section{Test, run and troubleshoot automations}
\label{sec:builder-feature-sops-testing}

A successful test proves more than that the flow ran: the intended event supplied the intended data, the condition made the right decision, the action affected only the approved target, and a reviewer can find the result. So you test the parts one by one with sample records, then turn the automation on for a small scope before widening it.

\textbf{Path and who uses it:} “SOPs” → the flow → testing each step, then the run history. Whoever builds the automation tests it, and the business owner confirms the result.

\begin{rcnote}[Example: Horizon]
The system administrator tests the automation with two sample requests: one for “Aleppo Branch” that should create a task for Sarah Al-Khatib, and one for another branch that should create nothing. Sarah then confirms that the task appeared only once.
\end{rcnote}

\end{rcwarn}

\begin{enumerate}

\item Cause the event on one sample record, and review the data that arrived before mapping any field.
\item Run one case that should continue and one that should stop, and confirm that the second created nothing.
\item Add the actions one after another, and after each run look for the result inside the app.
\item Turn the automation on for a small scope, review the first real runs, then widen it after the business owner agrees.
\end{enumerate}

\textbf{Check and recovery:} a test is complete when the reviewer finds the intended result with no duplicates or unintended effects, not when the test panel shows success. If a run fails, record its time, the event, the mapped values, the error message and the last step that succeeded, then correct one step only. For ready patterns, such as routing to a queue or preparing a document after approval, see the automation recipes in the product documentation.

\subsection{Steps and check}
\begin{enumerate}
\item Open “Bots”, press “Add Bot”, write the name in “Name” and press “Create”.
\item In the “Chat” section, turn on where it can be added and what members can do with it.
\item Turn on the “Emails” and “Calendar” sections if you need them, then press “Save” in the “Unsaved changes” bar.
\item In “Internal SOPs”, build an SOP that starts “On Direct Message to Bot”, select the bot in it, then publish it.
\end{enumerate}

\textbf{Check and recovery:} add the bot to a test chat and message it; the SOP should start and appear under “Runs”. If members do not see the option to add it, review the “Chat” switches and make sure you saved; if the bot does not reply, make sure the SOP is published and not paused. To delete a bot, press “Delete” in its row in the list and confirm in the “Delete Bot” dialog; the deletion cannot be undone.

\section{Bot default installation}
\label{sec:builder-feature-bots-default-installation}

The “Default installation” section on a bot's page decides whether the bot is added automatically, without members adding it themselves. You choose the chats it is installed in, whether it is installed in email and calendar, and whether members can remove it from each place. The section also sets which email messages the bot reaches by default, its most important privacy setting.

\textbf{Path and who uses it:} “Bots” → open the bot → “Default installation”. Used by those with bots permission after setting the bot's capabilities.

\begin{rcnote}[Example: Horizon]
For “Visits assistant”, the system administrator chooses “Channels only” in chat, so the bot is installed in channels such as the branches channel. In email they choose “Related” with the branches' email address only, not “All”.
\end{rcnote}

\subsection{Steps and check}
\begin{enumerate}
\item Open the bot from “Bots” and go to the “Default installation” section.
\item Turn on “Install in Direct Chats”, then choose “Channels only” or “Direct \& Channels” from the list.
\item Turn on “Install in Emails” if you need it, then press the button beside it to open “Default email access”, choose “Related” or “Labels”, and add the addresses or labels.
\item Turn on “Install in Calendar” if you need it, and select the “Can be removed from…” options that let members remove it.
\item Press “Save” in the “Unsaved changes” bar, or “Discard” to cancel the changes.
\end{enumerate}

\textbf{Check and recovery:} a save-success message should appear, and the chosen option should still show beside each switch when you reopen the bot. If access went back to “All” by mistake, open the button again, choose the narrower option and save. If the bot is not added where you expected, review the capability switches in the “Chat” and “Emails” sections.
