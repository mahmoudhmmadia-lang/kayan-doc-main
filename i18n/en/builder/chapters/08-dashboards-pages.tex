\section{Dashboards}
\label{sec:builder-feature-dashboards}

A dashboard is a page of numbers and charts that summarizes the work, such as the number of open or overdue requests. Every dashboard starts on the “Dashboards” page, where you create dashboards, arrange them in folders and decide who can reach each one. Building a dashboard's content happens in the dashboard builder, explained on the following pages.

\textbf{Path and who uses it:} “Builder” → “Core” → “Dashboards”. The “Create Dashboard” button appears for those allowed to create dashboards, and each user sees the cards they are allowed to open.

\begin{rcnote}[Example: Horizon]
The system administrator creates a “Branch services” folder, then creates the “Visits follow-up” dashboard inside it and gives Sarah Al-Khatib's role access to it. The dashboard starts from ①, and the folder from ②.
\end{rcnote}

\section{Dashboard builder: sections and widgets}
\label{sec:builder-feature-dashboards-builder}

The dashboard builder is where you build a dashboard's content. A dashboard is made of sections one after another; each section has a title, a description and a grid where you place widgets, and a widget is a figure, a chart, a table or something similar. “Save” keeps your changes as a draft, and viewers do not see them until you publish.

\textbf{Path and who uses it:} “Dashboards” → the dashboard card's menu → “Edit”. Used by those allowed to edit the dashboard; it also opens automatically after you create a new dashboard.

\begin{rcnote}[Example: Horizon]
The system administrator adds to “Visits follow-up” a section titled “Request status” with a figure for pending requests and a pie chart of requests by status, then a second section titled “Appointments” with a calendar of the visits.
\end{rcnote}

\section{Widget settings and data sources}
\label{sec:builder-feature-dashboards-widget-settings}

When you press a widget in the builder, its settings panel opens with three tabs: “General” for the title and size, “Data” for the source of the numbers and how they are calculated, and “Style” for colours and look. The data source decides where the widget takes its numbers from, and “Access Level” decides whether each viewer sees only what their permissions allow.

\textbf{Path and who uses it:} dashboard builder → press the widget → the settings panel. Used by whoever builds the dashboard; the “Data” tab opens first.

\begin{rcnote}[Example: Horizon]
For the pending-requests widget, the system administrator chooses the source “Entity” and the record type “Visit requests”, the value type “Count”, then adds a filter limiting the count to requests waiting for review. He chooses “User Permissions”, so Sarah Al-Khatib sees only her branches' requests.
\end{rcnote}

\section{Viewer filters and entity selectors}
\label{sec:builder-feature-dashboards-filters}

Viewer filters are controls at the top of the dashboard that let the viewer change what the widgets show without editing the dashboard. There are three kinds: “Date Range” to pick a period, “Selector” to pick a record of a record type such as a branch, and “Select Field” to pick a value from a list of options. Each filter has a “Scope” that decides which widgets it affects.

\textbf{Path and who uses it:} dashboard builder → “Filters”. Set up by whoever builds the dashboard, and used by everyone who opens it.

\begin{rcnote}[Example: Horizon]
The system administrator adds to “Visits follow-up” a “Date Range” filter on the visit date and a “Selector” for branches. Sarah Al-Khatib picks the Aleppo Branch and last month, and every widget shows that branch's visits in that period.
\end{rcnote}

\section{Preview, publishing and versions}
\label{sec:builder-feature-dashboards-publish}

The builder keeps your work as a draft that viewers do not see. “Preview” shows the dashboard as they will see it, then “Publish” creates a new version that replaces the published one. “Version history” keeps earlier versions, so you can return to any of them when needed.

\textbf{Path and who uses it:} dashboard builder → “Preview”, “Publish” or “Versions”. Used by those allowed to edit the dashboard.

\begin{rcnote}[Example: Horizon]
The system administrator previews “Visits follow-up” and sees that the number of pending requests matches the list, so he presses “Publish”. A week later he deletes a widget by mistake and restores the previous version from “Version history”.
\end{rcnote}

It shows that viewers see the published version, not the latest save in the builder. ① “Preview”: shows the dashboard as a viewer sees it. ② “Publish”: saves the draft and publishes it as a new version. ③ “Version history”. ④ “More options”: the version menu with “View” and “Restore”.}
\end{figure}

\begin{table}[H]
\centering
\caption{Preview and publishing tools}
\label{tab:builder-dashboards-publish-tools}
\begin{tabularx}{\linewidth}{R{3.6cm} Y}

\thh{Tool} & \thh{What it does}\\

“Publish” & Saves what is in the builder, then publishes it as a new version, and “Dashboard published successfully” appears.\\

\item Publish the dashboard again so the restored version reaches viewers.
\end{enumerate}

\textbf{Check and recovery:} a new version with the status “Published” should appear in “Version history”. If “Failed to publish dashboard. Please try again.” appears, save first, then publish again. If viewers see the old version, make sure you published after your last change.
